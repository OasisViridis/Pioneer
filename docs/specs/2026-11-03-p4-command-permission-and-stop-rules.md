# P4-D2 命令许可与停止规则决策（Issue #22）

日期：2026-11-03。来源：[Issue #22](https://github.com/OasisViridis/Pioneer/issues/22)，属于[主地图 #9](https://github.com/OasisViridis/Pioneer/issues/9) 的 P4 决策票。前置 [#18](https://github.com/OasisViridis/Pioneer/issues/18) 已关闭。

本规格只定义决策，不实现命令执行。命令能力保持关闭，直到 #23 按本规格实现并通过验收：没有注册工具名、没有新增 IPC 通道、preload 方法、Run 事件、失败码、能力位或进程执行器。仓库当前没有任何进程执行面：`apps/` 内没有 `child_process`、`spawn`、`execFile`、`utilityProcess`、`node-pty` 或 `worker_threads` 调用；现有四组 IPC 通道（目录、会话、运行、窗口；成品验收只覆盖其中不含窗口的运行相关通道）里没有接收可执行文件、参数、工作目录或环境变量的通道；[RunManager.executeTool](../../apps/desktop/src/main/harness/run-manager.ts) 只分发三个只读工具。

## 1. 本次决策与交付范围

| 项       | 内容                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |

| 不做     | 命令执行器、进程树控制、审批界面、事件字段、工具名、能力位、shell、交互式 stdin、真实命令运行                           |
| 前提     | #18 已关闭；#23 另依赖 #20                                                                                             |
| 决策对象 | 是否启用一个命令场景；若启用，授权、环境、文件、网络与停止规则                                                         |
| 不改变的 | 命令能力保持关闭；只读、写入、外发、发布四类许可的定义与实现不变                                                       |

本文用“命令许可”（Command Permission）指用户对一条已声明命令的显式批准。它与运行 Grant、只读许可、写入权限、发布授权都不是同一件事，见 §2。

## 2. 术语与许可关系

### 2.1 五类许可

| 许可                | 回答的问题                         | 记录位置                       |
| ------------------- | ---------------------------------- | ------------------------------ |
| 运行 Grant          | 这段任务与外发材料能不能发给模型   | 绑定本次 Run 与外发清单        |
| 只读许可            | 这个文件能不能被三个只读工具读取   | 只读工具请求与路径策略         |
| 写入权限            | 这个项目与作用域能不能替换文件     | 会话级权限选择器               |
| 命令许可（本票）    | 这条命令能不能现在启动             | 单次 Run 的命令许可记录        |
| 发布授权（未实现）  | 这次改动能不能对外发布             | 未来票；本票不定义             |

五类各自独立，不能互相代替：

- 有运行 Grant 不等于能起进程；Grant 只说明模型可以收到哪些材料，以及这次 Run 被允许开始。当前“execution”指的是开始一次 Run，不是启动操作系统进程。
- 只读许可与写入权限都不构成命令许可；反过来，命令许可也不扩大可读文件或可写路径。
- 命令许可不包含外发权限。命令输出是否进入模型上下文由 `outputToModel` 单独决定，见 §5.7。运行 Grant 与外发材料清单是这条权限的唯一来源。
- 命令许可不包含发布授权，也不授权模型自行选择 executable、参数或 shell 文本。
- 命令执行器自身造成的文件改动不受[变更日志](../../GLOSSARY.md)保护，也不能用 #20 的恢复流程撤销。见 §7.6。

### 2.2 与 GLOSSARY 的关系

[GLOSSARY](../../GLOSSARY.md) 的“写入授权”涵盖只读、外发、写入与发布四类。命令许可不并入这四类，作为第五类单独命名，避免把“能改文件”读成“能起进程”。本票已把“命令许可”与“声明检查”加入 GLOSSARY，#23 沿用该措辞。

## 3. 威胁模型

### 3.1 攻击者能力

| 编号 | 攻击者                                   | 能做什么                                                                                                 |
| ---- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A1   | 模型输出                                 | 选择工具与参数；受提示注入影响；不能直接写文件或起进程，只能通过宿主暴露的能力行动                       |
| A2   | 项目内容                                 | 测试、脚本、构建配置本身是代码；用户打开的项目可能不是自己写的                                           |
| A3   | 模型可写的项目文件                       | 在 #19 的写入权限下能替换已有文本文件；能否改命令配置取决于它是否在保护路径内                            |
| A4   | 本机同权限进程                           | 可读写用户能访问的一切；可替换 PATH 上的程序、修改项目文件、伪造输出                                     |
| A5   | 被攻破的 renderer                        | 可发任意 IPC 请求；不能绕过 main 的 schema 校验与身份绑定                                                 |
| A6   | 依赖供应链                               | 项目依赖的安装脚本、二进制包；只在用户运行安装类命令时进入执行面                                         |
| A7   | 应用自身缺陷                             | 可能把旧许可当新许可、漏杀子进程、把超时当成功、把部分副作用报告成无副作用                               |

### 3.2 受保护资产

1. P1 凭证：环境变量里的令牌、`~/.ssh`、`%APPDATA%` 下的登录态、浏览器 Cookie、云 CLI 配置。
2. P2 项目外文件：其他项目、用户主目录、系统目录、共享盘。
3. P3 网络与数据外发：命令把文件内容发往任意主机的可能性。
4. P4 主机完整性：后台进程、自启动项、计划任务、持久化写入。
5. P5 项目完整性：命令对工作区的创建、修改、删除。
6. P6 变更日志与 Run 历史：不能让命令的副作用看起来像应用自己的可恢复写入。
7. P7 用户注意力与机器资源：失控进程、CPU/内存占用、弹窗与交互式等待。

### 3.3 信任边界与前提

1. **用户信任自己的项目**。命令场景的前提是用户对该项目的代码有基本信任；本能力不把第三方仓库变成安全可执行对象。
2. **renderer 不可信**。审批事实由 main 从用户点击生成，renderer 不能上传 `approved: true`、程序路径、参数或环境变量。
3. **模型不可信**。模型只能按 ID 选择一条已声明命令，不能提供 executable、参数、工作目录或环境变量。
4. **操作系统是最后边界**。应用层检查、路径判断与参数白名单都不是内核隔离；Windows 上真正限制文件、网络与进程树的是 OS 机制，而首版不承诺这些机制。
5. **审批绑定预期的执行定义**。许可绑定程序路径、参数摘要、工作目录、环境变量名、超时与配置摘要；启动前复核程序身份，任一项变化即拒绝。程序替换的竞态不能消除，只能缩小窗口，见 §8.2 第 6 项。

### 3.4 不防御的威胁

| 编号 | 不防御                                             | 原因                                                                   |
| ---- | -------------------------------------------------- | ---------------------------------------------------------------------- |
| N1   | 命令读取任意用户可读文件                           | 没有文件系统隔离；环境变量过滤只减少继承，不阻止程序自己读文件         |
| N2   | 命令访问网络                                       | 没有按进程的网络限制；防火墙规则是整机或整应用级别，不是本能力可开的   |
| N3   | 命令写到项目外                                     | 同上；工作目录只是起点，不是写范围                                     |
| N4   | 命令打印出凭证后再由用户复制给别人                 | 应用不能识别任意秘密；只保证输出默认不进模型                           |
| N5   | 子进程主动脱离作业对象或提权                       | Windows 作业对象在常规配置下可覆盖普通子进程，但不是安全沙箱           |
| N6   | 同权限恶意本地进程替换程序或项目文件               | 应用层校验存在 TOCTOU；与 #18 §3.4 的残余竞态同类                       |
| N7   | 命令自身的逻辑错误、数据损坏或不可逆迁移           | 应用只报告退出状态与观察到的文件变化，不判断命令是否“做对了”           |

### 3.5 威胁与对策

| 威胁                                   | 首版对策                                                                 | 残余风险                                         |
| -------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| 模型拼出任意 shell 命令                | 模型只能选 `checkId`；程序与参数来自项目配置；`shell: false`             | 配置本身就是用户批准的代码，见下一行             |
| 提示注入改配置后再请求执行             | 配置放在写入保护路径；许可绑定配置 SHA-256；审批界面展示完整命令         | 用户点“批准”前不看内容                           |
| 旧许可被复用                           | 单次消费、短有效期、绑定 Run/revision/windowEpoch/配置摘要               | main 崩溃前的竞态，由启动恢复标记 unknown 处理   |
| 密钥经环境变量继承                     | 最小环境 allowlist；额外变量按名显式声明                                 | 程序仍可读文件；用户可能主动声明令牌变量         |
| 输出把密钥带进模型                     | `outputToModel` 默认关闭；开启后仍受 64 KiB 模型输入预算                 | 默认关闭时用户仍可能在界面看到密钥               |
| 失控进程                               | 作业对象 kill-on-close、单命令超时、Run 120 秒总时限                     | 脱离作业对象的进程；进程树确认失败时只能报固定失败 |
| 命令写坏项目文件                       | 前后有界扫描并列出观察到的变化；不声称回滚                               | 扫描排除项内的变化、扫描窗口外的变化             |
| 命令副作用被当成可恢复写入             | 变更日志只记录应用自己的替换；#20 恢复不得处理命令副作用                 | 用户可能误以为“停止”等于撤销                     |
| renderer 伪造审批                      | main 生成许可记录，renderer 只能请求与展示                               | 被完全控制的 renderer 仍可发起请求，但拿不到许可 |
| 依赖安装脚本                           | 首版场景不包含安装类命令                                                 | 用户声明的检查脚本可能间接调用安装               |

## 4. 场景比较：零命令与一个候选场景

### 4.1 零命令

| 维度     | 内容                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 产品     | 保持现状：读取、分析、写入与恢复；验证由用户手动执行后粘贴结果                                               |
| 工程成本 | 0 个新工具、0 个新 IPC、0 个新进程控制                                                                       |
| 安全风险 | 不增加新的执行面；命令能力继续关闭                                                                           |
| 论文与验收 | M3-G 记录“命令能力未实施”；#23 关闭为范围变更；验证仍靠人工                            |
| 用户代价 | 模型只能声称“改完了”，不能给出退出码；每次验证都要离开应用手动跑，再把结果贴回来                            |

零命令不是没有价值：它保住当前四类许可的完整性，也避免在 #20 完成前同时引入写入与命令两条副作用链。代价是产品最关键的“改完能不能跑”问题仍然靠人。

### 4.2 一个候选场景：项目声明检查（project_check）

| 维度     | 内容                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 产品     | 用户预先在项目里声明一条检查命令；模型只能按 ID 请求跑它；界面展示完整命令与范围后再批准                     |
| 工程成本 | 1 个工具名、1 份命令许可记录、1 个审批界面、1 个进程监督器、若干事件与失败码；需要原生作业对象或等价机制     |
| 安全风险 | 命令以用户权限运行；文件、网络、凭证读取都不可由应用层限制；只能靠审批、结构参数、环境 allowlist 与停止规则收窄 |
| 论文与验收 | 可以给出真实退出码、超时、停止与副作用记录；M3-G 有命令证据                                                  |
| 用户代价 | 每个要用命令的项目都要先写配置；审批步骤比只读工具多；失败与不确定状态要如实展示                             |

### 4.3 为什么需要一个具体场景

P4-A 的目标是让 Agent 能改文件，但没有执行能力时，验证只能回到“模型自述完成”。项目已经在多处规定不得把模型自述当成状态：只读阶段不接受假空成功，写入阶段要求写后回读。命令是唯一能给出外部退出码的手段，因此它不是锦上添花，而是把“修改”变成“可验证修改”的最后一环。

但命令也是目前风险最高的能力：它不受变更日志保护，不能回滚，且应用层无法限制文件与网络。因此本规格只支持一个场景，并把“无法防御”的部分写在审批界面和规格里，而不是用黑名单或字符串过滤假装隔离。

### 4.4 决策判据

1. 如果 #23 能在 Windows 上证明作业内收敛与许可失效，并如实报告作业外不可证明，采纳一个场景。
2. 如果证明不了，回退到零命令，并在 M3-G 记录范围变更；不得用 `taskkill` 或字符串过滤代替证明。
3. 任何情况下都不把命令能力描述成沙箱、容器或“安全隔离”。

## 5. 候选策略：项目声明检查

### 5.1 场景定义

首版只注册一个工具名（候选 `run_check`），只接受一个参数对象 `{ checkId: string }`。`checkId` 必须命中项目配置里声明的条目；未命中的请求在启动任何进程之前拒绝。一个 Run 最多成功启动一条命令；第二条请求拒绝为超限。命令计入 `RUN_LIMITS.toolCalls`（32 次，含拒绝）的现有计数，不另设豁免；命令仍占 `toolConcurrency: 1`，与只读工具串行。

模型不能提交程序、参数、工作目录、环境变量、超时或 shell 文本；这些全部来自配置与 main 的固定规则。

命名固定如下，避免同一概念出现多个名字：场景 ID 是 `project_check`；工具名候选 `run_check`；配置数组是 `checks`；数组里的单条叫“声明检查”。

模型上下文里只出现本次 Run 已批准的 `checkId`（首版最多一个），不出现未批准条目、程序、参数、环境变量值或配置正文。已批准的 ID 随运行授权摘要进入模型上下文，不另行扩大外发材料清单；未声明的检查对模型不可见。

### 5.2 配置

候选路径：项目根下的 `.pioneer/commands.json`。它是一个普通文件，不允许链接；main 直接读取，不经过只读工具，也不用模型提供路径。

```json
{
  "version": 1,
  "checks": [
    {
      "id": "verify",
      "program": "node",
      "args": ["./scripts/verify.mjs"],
      "cwd": ".",
      "timeoutMs": 60000,
      "envAllowlist": []
    }
  ]
}
```

| 字段           | 规则                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------- |
| `version`      | 只接受 `1`；其他版本拒绝加载                                                             |
| `checks`       | 最多 8 条；ID 唯一、区分大小写、1–64 字符、`^[a-zA-Z0-9_-]+$`                            |
| `program`      | 1–1,024 字符；绝对路径或裸名；裸名由 main 用清理后的 `PATH` 解析，结果写入许可记录       |
| `args`         | 0–16 项，每项 1–256 字符，不允许 NUL 与控制字符；总字节不超过 4 KiB                      |
| `cwd`          | 首版只接受 `"."`；解析后必须是项目根，且不是链接                                         |
| `timeoutMs`    | 5,000–110,000 的整数；默认 60,000；上限低于 Run 的 120 秒总时限，留出收敛时间             |
| `envAllowlist` | 0–16 个环境变量名，只传名字；值取自 main 进程环境；不传未列出的变量                       |

配置本身有 16 KiB 上限；解析失败、字段多余、重复 ID、非法字符都整份拒绝，不回退到“跳过坏条目”。配置的 SHA-256 写入命令许可，配置变化即让旧许可失效。

**配置的写入保护（建议，见决定表第 3a、3b 项）**：若确认把配置放项目内，`.pioneer/commands.json` 应加入写入权限的保护路径，`.pioneer` 目录的创建、删除、改名、替换也应拒绝；其他文件不因此被锁定。与 `.git` 一样，这些规则不能被用户配置移除。它需要 #23 修改写入权限契约，本票不改；未确认前不得把它当成已生效。

无论配置放哪里，#23 都必须逐段检查配置路径与父目录不是 reparse point，并在打开前后复核摘要；检查与打开之间的竞态接受，与 #18 §3.4 同类。

### 5.3 可执行文件与参数

| 项             | 规则                                                                                                                   |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 程序类型       | 首版只接受 Windows `.exe` 镜像；`.cmd`、`.bat`、`.ps1` 与解释器脚本一律拒绝                                             |
| 解析           | 绝对路径直接用；裸名用清理后的 `PATH` 查找，命中多个候选取第一个并记录；解析失败即拒绝；禁止当前目录、空路径段、相对路径与 `.`，结果必须是绝对路径 |
| 身份           | 许可记录保存解析后的绝对路径、文件大小、`ino` 与 `birthtimeMs`（平台不报告时记 `null`）与 SHA-256                       |
| 启动时复核     | 启动前重新核对路径、大小与哈希；不一致拒绝并提示重新审批                                                               |
| 参数           | 字符串数组，按 argv 逐项传递，`shell: false`；不做字符串拼接，不经过 `cmd.exe`                                          |
| 为什么拒绝垫片 | Windows 上 `.cmd`/`.bat` 不能由 `execFile` 直接启动，必须经 `shell` 或 `cmd.exe`，会把参数重新交给命令解释器 ([Node.js child_process](https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows))；CVE-2024-27980 修复后，不设 `shell` 直接启动 `.bat`/`.cmd` 会返回 `EINVAL` ([Node.js 安全公告](https://nodejs.org/en/blog/vulnerability/april-2024-security-releases-2)) |

这条规则会让 `pnpm`、`npm` 这类在 Windows 上是 `.cmd` 垫片的入口无法直接使用。首版接受这个限制：需要检查脚本时，声明 `node` 加脚本路径；把 `.cmd` 支持留给后续票，并先解决 `cmd.exe` 引号与元字符转义。

`.exe` 规则只避免 Node 隐式经 shell 启动 `.cmd` 垫片，不限制配置显式选择 `cmd.exe`、`powershell.exe` 或 `node.exe -e`。这些仍然是用户批准的任意代码；首版不用解释器黑名单假装限制，因为那只是字符串过滤，不构成边界。

### 5.4 工作目录

- 只接受项目根 `"."`。main 用目录册里的项目根解析，不接受模型或 renderer 提供的路径。
- 解析后必须仍在项目根内，且根与 `cwd` 都不是链接。
- 工作目录只是起点，不是写范围：命令可以 `cd` 到任何位置，见 §3.4 N3。

### 5.5 环境

main 构造最小环境，不继承完整 `process.env`：

| 分类     | 内容                                                                                       |
| -------- | ------------------------------------------------------------------------------------------ |
| 固定传入 | `Path`、`SystemDrive`、`SystemRoot`、`TEMP`、`TMP`（Chromium 给沙箱子进程的最小集合，见 [broker_services.cc](https://raw.githubusercontent.com/chromium/chromium/main/sandbox/win/src/broker_services.cc)） |
| 显式追加 | 配置 `envAllowlist` 里的变量名，值取自 main 进程环境；界面只显示名字，不显示值              |
| 不默认传 | `ComSpec`、`PATHEXT`、`USERPROFILE`、`APPDATA`、`LOCALAPPDATA`；需要时由 `envAllowlist` 显式追加 |
| 永不传入 | `NODE_OPTIONS`、`NODE_PATH`、`PYTHONPATH`、`PYTHONSTARTUP`、`PERL5OPT`、`RUBYOPT`、`BASH_ENV` 等能改变解释器行为的变量，即使配置列出也不传 |
| 敏感名   | 名称匹配令牌、密钥、密码模式的变量不自动继承；显式列出时必须经过一次风险确认                |

三个实现约束：

1. `PATH` 在 Windows 上大小写不敏感，Node 按字典序只取第一个匹配项；同时存在 `Path` 与 `PATH` 时可能取错 ([Node.js child_process](https://nodejs.org/api/child_process.html#optionsenv))。main 必须自己构造唯一键名的环境块，不直接复用 `process.env`。
2. `spawn` 的 `env` 默认就是 `process.env`；不显式传 `env` 就等于完整继承。
3. `Path` 的值取自 main 进程的 `Path`，与 Chromium 的做法一致；因此命令内部再按名字启动其他程序时仍使用用户的 PATH。这不构成安全边界，只是让普通工具能跑。

环境过滤只减少“把密钥顺手交给子进程”，不阻止程序自己读文件。访问检查由令牌的 SID 与 DACL 决定，环境变量只是字符串 ([Access Tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-tokens))。规格与界面都不得把它写成隔离。

审批时 main 冻结实际环境块（键与值）并计算摘要，许可绑定该摘要；启动使用同一份快照，不在启动时重新读 `process.env`。程序解析与子进程使用同一份 `Path`。快照是不可变的内存对象，随许可消费、撤回、过期或 Run 终止释放，不持久化秘密值，摘要也不含明文。变量名匹配大小写不敏感。

### 5.6 文件与网络范围

| 范围     | 如何授权或仍待决                                                                     |
| -------- | ------------------------------------------------------------------------------------ |
| 文件读取 | 应用层无法限制。审批界面明确写“该命令以你的用户权限运行，可读取你可读的文件”          |
| 文件写入 | 应用层无法限制。审批界面明确写“可能修改项目内外文件，停止不撤销”                     |
| 网络     | 应用层无法限制。审批界面明确写“可能访问网络”；首版不提供网络开关                     |
| 生效边界 | 只有工作目录、环境变量、程序与参数是受控的；文件与网络不受控                         |

不提供“只读命令”这一档，因为无法验证。也不提供“网络关闭”按钮，因为没有按进程的执行机制。

真正的系统级控制存在，但都不在本票范围：

| 机制                | 实际能力                                             | 首版不采用的原因                                     |
| ------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| AppContainer        | 隔离文件、注册表、网络与进程                         | 未打包程序需自建 profile，官方文档称其复杂；属独立票 |
| 受限令牌            | 去特权、加 deny-only SID；对网络无效                 | 文件限制要自建 deny SID；不能当网络控制              |
| Windows Sandbox     | 独立虚拟机，可关网络                                 | 仅 Pro/Enterprise/Education，不是按进程启动          |
| 防火墙规则          | 机器或镜像级网络策略                                 | 需要管理员交互，无法按次授权                         |
| Job 对象安全限额    | 只限制子进程创建等少数项                             | 不含路径与网络过滤；见 §7.1                          |

首版不声称以上任何一项已生效；它们属于 #23 之后的独立决策。

### 5.7 输出与模型外发

- stdout 与 stderr 分开捕获，各上限 64 KiB，合计 128 KiB；超限截断并标记 `truncated`。达到上限后继续读取并丢弃，直到进程退出，避免管道写满把子进程卡死；截断不是失败。
- 输出按 UTF-8 解码；遇到非法字节记 `decodeLossy: true`，界面提示可能存在乱码。是否乱码取决于程序实际写出的字节编码，可能是 ANSI 代码页；首版不猜测代码页，也不自动切换。
- `outputToModel` 默认 `false`。关闭时模型只收到退出码、时长、字节数与截断标记，不收到正文；正文只在界面展示。
- 开启时正文计入 Run 的 64 KiB 模型输入预算，并按固定规则截断；审批界面必须提示“输出可能包含凭证”。
- `outputToModel: true` 只是必要条件：还要有 Run Grant 与外发材料清单允许。缺任何一项都不发送，不能凭界面勾选单独放行。
- 不做秘密扫描。规格与界面都不得承诺“已检测并移除密钥”。

### 5.8 预算与并发

| 项       | 值                                                                 |
| -------- | ------------------------------------------------------------------ |
| 并发     | 每个 Run 同时最多 1 条命令；全局沿用 `toolConcurrency: 1`           |
| 数量     | 每个 Run 最多成功启动 1 条命令                                     |
| 超时     | 单命令 5–110 秒，默认 60 秒；到点强制结束，不自动重试               |
| 输出     | 128 KiB 合计上限                                                   |
| stdin    | 关闭（`ignore`）；命令等待输入时按 EOF 处理，可能失败               |
| 重试     | 不自动重试；用户重新发起等于新的 Run 与新的许可                    |

### 5.9 退出码语义

进程正常结束（退出码 0 或非 0）都算成功的工具调用，结果携带 `exitCode`、时长与截断标记；非零退出码不自动让 Run 失败，模型可以据此解释测试失败。

只有下列情况算工具失败并走固定码：无法启动、超时、停止未确认、读取输出失败（管道错误）、平台不支持、许可或配置失效。输出截断不算失败。

被宿主强制终止时，结果记 `terminatedBy: 'host'` 与终止原因，不给程序自己的 `exitCode`；`exitCode` 只在程序自然退出时出现，不得把 0 或猜测值写成退出码。

读取输出失败时，立即关闭新命令准入、终止作业对象并确认受控树收敛；确认不了按 §7.2 的不确定规则处理，不能留下一个还在写管道的进程。

### 6.1 字段

| ------------------------------------------ | ----------- | ---------------------------------------------------------- |
| `sessionId` / `projectId` / `runId`        | main        | 绑定到哪个会话、项目与 Run                                 |
| `revision`                                 | main        | 任务修订；修订变化即失效                                   |
| `windowEpoch`                              | main        | 只允许当前窗口使用                                         |
| `scenario`                                 | 固定枚举    | 首版只有 `project_check`                                   |
| `checkId`                                  | 用户选择    | 配置里的条目 ID                                            |
| `programPath` / `programSha256` / 身份      | main        | 实际要启动的镜像与身份                                     |
| `argvDigest`                               | main        | 参数数组的摘要，避免把完整参数写进日志                     |
| `cwd`                                      | main        | 解析后的项目根                                             |
| `envKeys`                                  | main        | 实际传入的变量名集合                                       |

| `grantedAt` / `expiresAt` / `consumedAt`    | main        | 授予、过期、消费时间；有效期不超过 5 分钟                  |

### 6.2 生命周期

- **创建**：在 `run:authorize` 阶段完成，早于 `run:start`。用户看到要运行的命令后点击批准，main 生成记录；renderer 只能发起“请求授权”，不能提交批准事实。`run:start` 才启动 120 秒 Run 计时；拒绝则不创建 Grant、不启动。运行中不再弹审批：没有许可时 `run_check` 返回固定拒绝，模型只能说明需要一次新的 Run，用户重新授权后由新 Run 执行。
- **单次使用**：启动进程时原子消费；`consumedAt` 之后同一记录不能再启动第二条命令。启动失败也算消费，重试需要重新批准。
- **失效**：过期、Run 进入终态、切项目、窗口代次变化、配置摘要变化、程序身份变化、用户撤回，任一发生即拒绝新进程。
- **复核**：每次启动前由 main 重新核对 `runId`、`revision`、`windowEpoch`、`sessionId`、`projectId`、配置摘要、环境摘要、程序身份与剩余有效期；不缓存“已批准”。
- **原子启动**：最终复核、许可消费、创建挂起进程与恢复执行在 Run 状态机的同一个串行步骤里完成。停止已提交则拒绝启动；启动步骤先提交时，随后的停止在作业内结束该进程。不存在“许可已消费、停止已开始、进程随后才创建”的顺序。
- **环境快照**：审批时冻结为不可变内存对象，许可记录只存摘要；消费、撤回、过期或 Run 终态后释放，不写日志、不持久化。
- **展示**：界面展示解析后的程序绝对路径、参数、项目相对工作目录、超时、环境变量名、`outputToModel` 状态与三条风险提示。程序绝对路径是展示例外：用户必须知道要运行哪个镜像。

### 6.3 与运行 Grant 的关系

命令许可不在运行 Grant 里复用字段，也不用 `grantId` 存。一次 Run 可以没有命令许可；没有命令许可时 `run_check` 一律拒绝，不能回退到只读工具或 shell。反过来，命令许可不能延长 Grant、扩大外发材料或改写任务修订。

## 7. 停止、超时、子进程、崩溃与部分副作用

### 7.1 进程容器

首版要求用 Windows 作业对象承载命令进程树，设置 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，由 main 持有句柄。作业对象关闭时系统结束其中所有进程；`TerminateJobObject` 用于主动结束当前关联到该作业的进程 ([Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject))。

必须先说清作业对象的边界：

1. **作业对象不是安全边界**。它提供资源与 UI 限额，不提供文件、网络或路径过滤；不能拿它证明“命令无法访问某目录”。([Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects))
2. **必须在创建时关联**。`AssignProcessToJobObject` 是事后关联，子进程可能在关联完成前已经起了孙进程，形成时序窗口。正确做法是用 `PROC_THREAD_ATTRIBUTE_JOB_LIST` 在 `CreateProcess` 时挂上作业，并以 `CREATE_SUSPENDED` 启动后恢复 ([UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute))。这条要求把 Windows 下限抬到 10；首版接受。
3. **只有不加 breakaway 标志才谈得上整棵树**。设置 `JOB_OBJECT_LIMIT_BREAKAWAY_OK` 或 `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` 后，子进程可用 `CREATE_BREAKAWAY_FROM_JOB` 脱离；首版两个都不设 ([Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags))。
4. **已知逃逸面**：通过 WMI `Win32_Process.Create` 创建的进程不自动关联到调用者的作业，文档明确说明这一点 ([Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects))。命令自己调用 WMI 就能让孙进程脱离；首版唯一能做的是在结果里如实报告“作业内进程数已为 0，但无法证明没有作业外进程”。
5. **嵌套作业**：子进程默认继承父进程的作业；Windows 8 起支持一个进程同时属于多个作业，是否可脱离由最内层作业决定，有效限额取链上更严者 ([Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs))。Electron 主进程是 Chromium 的 broker 进程，不在 renderer/GPU/utility 那批作业里，但它可能被安装器、IDE runner 或沙箱启动器放进外层作业；实现必须先探测并记录，不能假设自己是第一个作业。
6. **Node 没有作业对象 API**。`child.kill()` 在 Windows 上只强制结束该 PID，不结束孙进程，且 PID 复用可能打到别的进程 ([Node.js child_process](https://nodejs.org/api/child_process.html#subprocesskillsignal))。绑定作业对象需要原生 addon 或独立 helper。
7. **替代方案不能当证据**：`taskkill /T` 按当前 PID 关系枚举后结束，存在枚举与结束之间的竞态；`Stop-Process` 只按 Id 结束单进程；`Win32_Process.Terminate` 只结束该进程及其线程。三者都不看作业对象，不能用来证明收敛 ([taskkill](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill)、[Stop-Process](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.management/stop-process)、[Win32_Process.Terminate](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/terminate-method-in-class-win32-process))。
8. **句柄所有权**：`KILL_ON_JOB_CLOSE` 只在最后一个作业句柄关闭时触发，不是 main 单独关闭就触发。句柄不得被继承；若用独立 helper，helper 必须在 main 退出后关闭句柄或自行退出，否则 main 崩溃后命令进程会继续运行。这条必须有实测。

首版要求：停止结果必须来自“直接子进程已退出”加“作业对象内活动进程数为 0”两项观察。任一项拿不到，记固定失败，不显示“已停止”。

### 7.2 停止

停止顺序固定：

1. 关闭新准入，标记 Run 为 `stopping`。
2. 撤回命令许可，拒绝后续命令请求。
3. `TerminateJobObject` 结束整棵树。
4. 等待直接子进程退出事件，并核对作业对象内活动进程数为 0。
5. 追加唯一终态：作业内确认收敛记 `stopped`；直接子进程退出事件或作业计数拿不到，记 `failed(STOP_TIMEOUT)` 或 #23 定义的专用固定码。

这里必须区分两种“不确定”：

- **受控树不确定**：拿不到退出事件、作业句柄失效、计数查询失败。这是运行状态问题，按固定失败处理，不显示“已停止”。
- **作业外不确定**：命令通过 WMI 或其他方式在作业外起了进程。应用没有任何观察手段，只能把“作业外进程无法证明已结束”写进结果；这不把作业内已收敛的事实改写成失败，但也不允许显示“全部结束”。

5 秒停止宽限沿用 Run 合同。宽限到期只表示“不再等”，不表示“已结束”；界面在确认前一直显示“正在停止”。

本规格对 #23 “不确定时如实返回固定失败”的解释：这里的“不确定”指**受控树**不确定；作业外不可观察是已知限制，不改变作业内收敛时的 `stopped` 判定，但必须随结果披露。该解释需要在 #23 验收时确认。

停止与启动的竞争由同一状态机定序：停止请求先进入，启动被拒绝；启动步骤先提交，停止在作业内结束该进程。两种顺序都不允许出现“停止已开始、进程随后创建”。

### 7.3 超时

单命令超时与 Run 总时限都可能先到：

| 触发                 | 动作                                             | 记录                                             |
| -------------------- | ------------------------------------------------ | ------------------------------------------------ |
| 单命令 `timeoutMs`   | 实际超时取 `min(timeoutMs, 剩余 Run 时间)`；结束作业对象 | 工具结果 `failed(COMMAND_TIMEOUT)`；Run 失败     |
| Run `RUN_LIMITS.runMs` | 走停止流程，原因 `deadline`                     | 工具结果 `cancelled`；宽限内收敛 `stopped`；强制结束 `failed(RUN_DEADLINE)` |
| 结束失败             | 不重试，保留进程句柄状态                         | 固定失败码，界面列“可能仍在运行”                 |

两种超时不能混用：单命令超时是工具失败并让 Run 失败；Run 总时限是停止请求，工具结果记 `cancelled`，不记 `COMMAND_TIMEOUT`。先提交的终态优先，后到的成功结果不能覆盖。

超时不是成功，也不是“已停止”。不得把超时后的部分输出当作完整结果，除非截断标记清楚。

### 7.4 子进程与孙进程

- 作业对象覆盖普通子进程与孙进程。未设置 breakaway 限额时，子进程即使创建新作业或调用 `CREATE_BREAKAWAY_FROM_JOB` 也不会自动脱离父作业；嵌套作业仍受最内层限额约束。
- 真正需要单列的逃逸面是通过 WMI 创建的进程，以及显式允许 breakaway 的配置（首版不使用）。结果只描述作业内进程数，并单列“作业外不可证明”。
- 界面展示“已结束的进程数”与“作业内活动进程数”；不展示 PID、命令行或用户不可见的绝对路径。

### 7.5 崩溃与重启

- main 崩溃或退出时，作业对象句柄由系统关闭，`KILL_ON_JOB_CLOSE` 结束其中的进程。若用独立 helper，必须验证 main 被杀后 helper 不再持有句柄，否则本条的保证不成立。
- 崩溃前没有写入终态记录的 Run，重启后按既有规则标为 `unknown`/`host_restarted`；命令是否完整执行未知，副作用未知，绝不自动重跑。
- 重启只恢复历史材料与提示，不重建命令许可，也不重放旧请求。

### 7.6 部分副作用

命令的文件改动不写变更日志，也不能用 #20 的恢复计划撤销。可核对的范围只有：

1. **进程结果**：退出码（仅自然退出时存在）、是否被宿主结束及原因、开始与结束时间、时长、输出字节数与截断。
2. **工作区元数据对比**：启动前与结束后各做一次有界扫描，记录项目内文件路径、大小与修改时间；对比后列出新建、修改、删除的路径，最多 200 条，超出记 `truncated`。这只能算“观察到的元数据变化”：同大小、同修改时间的改动可能漏检，不能据此宣称“项目未变”。
3. **明确的排除项**：扫描默认排除 `.git`、`node_modules`、构建产物目录与临时目录；排除项必须在结果里列出。排除项内的变化不可见。

扫描只在作业内确认收敛后执行；未确认收敛时结果标为临时，不能当作最终副作用清单。

呈现规则：

- 结果区分开写“退出状态”“观察到的文件变化”“网络：不可证明”“未核对的范围”。
- 网络副作用没有观察手段，结果固定写“网络：不可证明”，不能省略或留空。
- 停止与失败都不能说“已回滚”或“项目未变”。
- 扫描对比不是文件快照，不保存内容，不提供恢复；#20 不得把命令副作用纳入恢复。
- 扫描窗口内、排除项外但未被观察到的变化（例如快速创建又删除）视为不可确认。

### 7.7 取消与部分输出

用户停止时，已产生的输出保留并标记 `cancelled`；不追加“成功”。命令已经退出但没有终态记录时，按 §7.5 处理。

## 8. 拒绝路径

### 8.1 拒绝码（候选，最终由 #23 落到契约）

| 组       | 码                                                                                                                       | 触发                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 许可     | `COMMAND_PERMISSION_REQUIRED`、`COMMAND_PERMISSION_EXPIRED`、`COMMAND_PERMISSION_REVOKED`、`COMMAND_PERMISSION_BINDING_MISMATCH` | 没有、过期、撤回、Run/窗口/项目不符 |
| 配置     | `COMMAND_CONFIG_UNAVAILABLE`、`COMMAND_CONFIG_INVALID`、`COMMAND_CONFIG_CHANGED`、`COMMAND_NOT_DECLARED`                  | 配置缺失、解析失败、摘要变化、ID 未知   |
| 程序     | `COMMAND_PROGRAM_NOT_FOUND`、`COMMAND_PROGRAM_NOT_ALLOWED`、`COMMAND_PROGRAM_CHANGED`、`COMMAND_CWD_INVALID`              | 解析失败、非 `.exe`、身份变化、目录越界 |
| 运行     | `COMMAND_ALREADY_RAN`、`COMMAND_CONCURRENCY_EXCEEDED`、`COMMAND_SPAWN_FAILED`、`COMMAND_TIMEOUT`、`COMMAND_STOP_UNCONFIRMED` | 重复、并发、启动失败、超时、停止未确认 |
| 平台     | `COMMAND_PLATFORM_UNSUPPORTED`                                                                                            | 非 Windows，或作业对象不可用           |

所有拒绝返回结构化对象，不反射绝对路径、命令行、环境变量值、原始 OS 异常或文件内容；界面只显示固定文案与用户可理解的操作。

### 8.2 不可验证条件

以下条件在首版无法证明，必须在规格、验证记录与界面中如实列出：

1. 命令是否访问了网络，访问了哪里。
2. 命令是否读取了项目外文件或凭证。
3. 命令是否写到项目外、系统目录或注册表。
4. 命令输出是否包含秘密。
5. 作业对象外是否还有残留进程（脱离、提权或枚举失败）。
6. 程序在许可创建与启动之间是否被替换（只能缩小窗口，不能消除）。
7. 扫描排除项内是否发生文件变化。
8. 命令逻辑是否正确、是否造成不可逆迁移。
9. 命令是否通过其他方式（服务、计划任务、驱动）留下持久化。

这些条件不能靠命令黑名单、字符串过滤或“安全模式”措辞变成已证明；规格禁止把它们写成隔离。

## 9. 与 #19、#20 的交叉约束

| 约束       | 内容                                                                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| 配置保护   | 只有决定表 3b 获确认后，`.pioneer/commands.json` 与 `.pioneer` 目录结构操作才进入保护；未确认时本规格不要求修改写入权限契约 |
| 日志边界   | 命令的文件改动不写入变更日志；#20 恢复只处理变更日志里的 `intent`/`applied` 记录，不处理命令副作用           |
| 部分完成   | 写入批次的部分完成与命令的部分副作用分开呈现，不能合并成一条“已完成”                                        |
| 外发预算   | 命令输出进入模型时占用 Run 的 64 KiB 输入预算；超预算拒绝或截断，不能绕过 Grant                             |
| 修订       | 命令许可绑定当前 `revision`；#19 的文件写入不推进任务 revision，只有任务文本或上下文变化才推进，因此写入不会让命令许可失效；配置或程序身份变化会让它失效 |
| 顺序       | #23 在 #20 完成后才能实现；#22 的确认不解除 #23 的原生依赖                                                   |

#23 的完成条件里有两处需要按本规格改写，否则无法如实满足：

1. “成功、失败、超时和停止显示实际退出状态及已知文件/网络副作用”：文件副作用只能给出前后有界扫描观察到的变化，网络副作用没有任何观察手段。可显示的只有“无法证明”，#23 验收时必须接受这个限制，或由人类明确修改该条件。
2. “停止结果基于受控进程及子进程收敛证据”：作业对象不是安全边界，WMI 或 breakaway 可让进程脱离。可证据化的只有作业内收敛，作业外只能报“不可证明”。#23 不得把“作业内为 0”写成“全部结束”。

## 10. #23 的验收要求

#23 必须留下以下证据，缺一项不得声称命令能力可用。若 #23 认为某项超出其范围，须由人类调整验收条件，不能自行降低标准。

1. **进程树**：在 Windows 上启动一个会再起孙进程的测试命令，停止后证明直接子进程退出且作业内活动进程数为 0；同时记录一次通过 WMI 创建进程的负向样例，证明首版如实报告“作业内已清空、作业外无法证明”，而不是声称全树已结束。若 Electron 已在外层作业、嵌套作业创建失败或不支持创建时关联，拒绝启动，不退化为事后 `AssignProcessToJobObject`。
2. **许可失效**：过期、配置变化、程序哈希变化、Run 终态后复用、跨窗口使用，全部拒绝且不创建进程。
3. **参数边界**：`.cmd`、`.bat`、`.ps1`、含 NUL/控制字符的参数、超过 16 项的参数、超长 ID、未知字段，全部拒绝且不创建进程。
4. **环境**：只传入 allowlist 列出的变量；未列出的令牌变量不在子进程环境里；显式列出的变量按用户选择传入；审批时冻结的环境摘要与启动时一致。
5. **输出**：`outputToModel: false` 时模型上下文没有任何命令正文；为 `true` 时按预算截断；截断后继续排空管道，进程不会因管道写满而卡住。
6. **超时与停止**：超时结束整棵树，结果显示实际退出状态；强制终止不给程序退出码；停止确认前不显示“已停止”。
7. **副作用**：前后扫描列出新建/修改/删除路径与排除项，并固定写“网络：不可证明”；停止与失败都不声称回滚。
8. **崩溃**：杀死 main 后重启，历史 Run 标记 unknown，作业内进程不残留，作业外标记不可证明，命令不自动重跑。
9. **文书**：界面与文档不出现“沙箱”“隔离”“安全执行”等未经证明的措辞；验证记录写明 NOT_RUN 项。
10. **门禁**：定向 Contract 探针、`pnpm verify:repository` 与完整 `pnpm check` 退出码 0；Windows 人工记录、成品包内依赖检查与上述结果绑定同一候选版本。

## 12. 留给 #23 的实现前决定

1. 作业对象的实现方式：原生 addon、独立 helper 进程或其他可验证方案；必须用创建时关联（`PROC_THREAD_ATTRIBUTE_JOB_LIST` + `CREATE_SUSPENDED`），处理 Electron 被外层作业包含的情况，并保证句柄不被 helper 继承、helper 在 main 退出后关闭句柄。
2. 事件与工具结果的字段：退出码、时长、截断、进程计数放在现有 `tool.result` 还是新增事件；新增失败码的最终命名。
3. 审批界面的实际文案与放置位置；是否复用运行授权面板；运行中不弹审批的交互如何告知用户。
4. 命令输出乱码的处理：是否允许用户选择代码页，或只显示 `decodeLossy` 提示。
5. 副作用扫描的排除目录清单与上限；是否允许用户项目覆盖。
6. Windows 版本下限与 32 位进程的处理。
7. `.cmd` 垫片是否在后续票支持，以及支持时如何避免 `cmd.exe` 元字符注入。
8. 单 Run 一条命令是否放宽；放宽前需要什么证据。
9. 命令许可是否持久化；建议不持久化，崩溃即失效。
10. 环境快照的存储位置与摘要算法；审批前是否允许用户编辑额外变量。
11. 输出排空策略与截断点；管道读取错误如何映射为固定码。
12. 成品包内依赖检查的具体命令与记录格式（#23 验收要求）。
